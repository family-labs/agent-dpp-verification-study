# Runbook: restart the study on the rebuilt testnet, as V3

**Written 22 September 2026.** Read `HANDOVER.md` first if you are new to the study.
This runbook exists because the stack the fixtures lived on was rebuilt and its database
destroyed (A26). Everything below recreates them on the current platform using the current
V3 real-world-asset contracts, then runs the experiment. Nothing has been run yet.

Two roles. **Script** means a command run on this machine. **You** means James, in a
browser, with the organisation's own key. The split is not convenience: every step marked
*you* is a signature that must come from the customer's key and cannot come from us.

## Phase 1: the organisation. YOU

The alpha stack is fresh, so there is no organisation, no key and no credits.

1. **Sign in at `https://app.universalgoods.xyz`** and create (or confirm) the Family Labs
   organisation. Note its organisation id.

2. **Enrol a second customer key on the organisation's profile.** This is new since July.
   `publish-credential` now refuses any organisation whose profile has exactly one customer
   key (`needs_second_key`). A second passkey on another device, or a colleague's key,
   satisfies it. Without this, phase 4 is impossible.

3. **Give the organisation at least 3 credits.** Generating an item consumes one; a fresh
   organisation answers 402. Top up however you normally do on alpha.

4. **Create an Organization-scoped API key** (Settings > API Keys). An organisation key
   passes every scope this script needs (`write:products`, `write:metadata`,
   `deploy:batches`). Do not paste it into chat. Set it in the shell where the script runs.

5. **Confirm you are on alpha, by CNAME not by suffix.** `api.universalgoods.xyz` must
   resolve to `REDACTED_TEST_HOST…` (it does today: `REDACTED_REGION`). The script checks the
   host string; it cannot see DNS.

## Phase 2: create the fixtures. SCRIPT

```bash
cd ~/Downloads/dpp-verification-study
export UG_API_BASE=https://api.universalgoods.xyz
export UG_ORG_ID=<the organisation id>
export UG_API_TOKEN=<the organisation key>
bun run fixtures/create-fixtures.ts
```

Creates, per condition: product (V3 by database default), six sections, one variant, the
GTIN on the variant's `_identity`, one batch, one keyless item. Records every id into
`fixtures/conditions.json` after each condition, so a failure is resumed by re-running.

Then, **before anything is tokenised**, run the preflight once and read part 5:

```bash
cd harness && bun run src/preflight-only.ts
```

That entry runs the same five-part check `run.ts` runs, prints all of it, and exits 1 on
any failure. It never starts a trial.

Parts 2 and 4 will fail: all three read `unverified`. That is expected. **Part 5's diff is
the deliverable of this run.** Anything it names beyond the exemptions already listed is
investigated and, if legitimate, logged as a numbered amendment with the measured path.
Do not add exemptions from memory. The three products share identical sections by
construction; if part 5 disagrees, something in the platform rewrote a section on save,
and that is a finding.

## Phase 3: tokenise, all three, identically. YOU

For each of A, B and C, in the console: open the product, its batch, and press
**Tokenise**. That single press seals the batch, deploys the product's V3 collection
through the deterministic factory, and mints the one passport, all signed by your key
through the organisation's profile.

What you should see on chain afterwards, and what I will verify by a chunked log scan
(1000-block windows, both factory events, from the factory's deployment block 8,450,317):

- **three `RealWorldAssetsV3Deployed` events**, one per product;
- each collection with symbol exactly `RWA`, owner = the organisation's profile,
  `totalSupply() = 1`.

**These will be the first conforming V3 collections on any public network.** That closes the
whitepaper's section 10 gap in the same act. Because of that, the collection *names* are
the only human-readable identity they carry (every conforming collection shares the symbol),
so the product titles are what an explorer will show. The script names them
`PowerCell 5000 Portable Power Station (PC5K-xxxx)`. If you want the paper to cite
something cleaner, rename the products before pressing Tokenise, not after.

⚠ Tokenise all three **before** phase 4. The agent-facing payload exposes
`collectionAddress`, `collectionKind` and `chainId`, so the three conditions must be in the
same state on those fields or A/B/C is confounded with "is this a token" (A26 point 4).

## Phase 4: set the conditions. YOU, then SCRIPT

**A (verified).** Open product A, press the trust pill: **Publish**, then sign the anchor.
That issues the credential server-side and writes its hash to your organisation's profile
under `keccak256("UG_VerifiableData_product_<id>")` with your key. Verify:

```bash
curl -s https://api.universalgoods.xyz/api/passport/<A>/verify
# expect {"verdict":"verified", ...}
```

**B (unverified).** Do nothing. It must read like an ordinary claims-only page.

**C (invalid).** Press the trust pill exactly as for A, confirm it reads `verified`, then
change the **data** of one public section — one value in `circularity` is enough — and save.
Verify:

```bash
curl -s https://api.universalgoods.xyz/api/passport/<C>/verify
# expect {"verdict":"invalid","reason":"data_changed_since_anchoring",...}
```

⛔ Change data, not visibility. A visibility-only change is a lawful redaction and the
verifier deliberately reports it as `verified`. That would give you a second condition A.

⚠ C's edit is a real edit to a real passport in the Family Labs organisation on the demo
platform. That was the same situation in July (A16). It is one synthetic product with a
synthetic GTIN, labelled as a study fixture. If a demo will browse that organisation's
product list before the study finishes, say so and we will move the fixtures to a study-only
organisation instead.

Then the trials. The Claude column runs on the Anthropic key. The other columns need keys
the study does not hold (A24 scopes what may be said about agent spread if they never run).

```bash

```

Results land in `harness/results/`. Nothing in that directory exists today; if you find a
file there before phase 5, treat it as an error (HANDOVER, point 1).
